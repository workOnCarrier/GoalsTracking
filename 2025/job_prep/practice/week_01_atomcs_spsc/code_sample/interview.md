# Atomic Counter Interview Notes

## Atomics and Lock-Freedom
`std::atomic<T>` gives the compiler and CPU explicit permission to generate indivisible read-modify-write instructions, so every thread observes entire values rather than torn writes. In the counter implementation that means two threads calling `increment()` cannot both read the same old value, add one, and store conflicting results. When comparing to a plain `std::int64_t` guarded only by convention, emphasize that the Standard labels any concurrent read/write without synchronization as a data race with undefined behavior, so atomics are the minimal building block for correctness.

Lock-free code promises that at least one contending thread completes its operation in a finite number of steps. Explain that lock-free does **not** mean contention-free; instead, it avoids kernel-level blocking and priority inversion by relying on hardware primitives such as `fetch_add`, which is effectively a load-linked/store-conditional (LL/SC) or compare-and-swap loop executed entirely in user space. Contrast this with wait-free structures, which guarantee every thread completes in bounded time, and mention livelock scenarios where all threads repeatedly collide yet none block—still lock-free but not wait-free.

## Memory Ordering
Atomic operations must also describe how they interact with surrounding loads/stores. `memory_order_relaxed` in the counter’s arithmetic methods only guarantees atomicity, making it perfect for pure counting where no other data depends on the ordering. However, if the counter is used to decide when producers and consumers can see shared work, interviewers may expect you to use `memory_order_acq_rel` or `memory_order_release`/`memory_order_acquire` pairs so that updates to other variables become visible alongside the counter change. `memory_order_seq_cst` is the strongest option, providing a single global order for all sequentially consistent operations; our `get()` and `reset()` default to it so readers can reason about a total ordering without additional fences. Be ready to justify relaxing those defaults if profiling shows they are on the hot path.

## ABA and CAS
Although `fetch_add` hides the explicit compare-and-swap loop, internally it still performs a read-modify-write that is susceptible to the ABA problem when the counter value is reused as a token. Imagine a freelist index that goes A→B→A again; another thread may see the same numeric value and assume nothing changed even though the resource was removed and reinserted. Mitigation techniques include tagging the counter with version bits (double-width atomics), hazard pointers, or epoch-based reclamation. Be prepared to explain when a simple monotonic counter is immune (e.g., when overflow is impossible or the value is never reused as an identifier).

## Overflow and Signedness
The sample uses `std::int64_t` to give a large symmetric range and to match typical telemetry counters that dip below zero. Interview questions often explore what happens when the counter exceeds `INT64_MAX`. Per the Standard, signed overflow on two’s-complement hardware is well-defined for atomic fetch-add (it wraps the same way as the underlying type), but relying on wraparound may surprise consumers. Discuss alternatives such as using `std::uint64_t` when only non-negative counts are needed, introducing checks that clamp at domain-specific maximums, or splitting work across sharded counters to lower the risk entirely.

## Testing Strategies
Concurrency bugs are timing-sensitive, so tests must mix deterministic checks with stress runs. The provided test launches multiple threads and millions of increments to expose obvious data races, yet that still cannot prove absence of bugs. Mention using ThreadSanitizer (`-fsanitize=thread`) to detect races, model checkers like CDSChecker for small state spaces, and fuzzers that vary thread counts and scheduling. For CI-friendly runs, keep iteration counts modest to maintain fast feedback while reserving heavier stress tests for nightly builds.

## Practical Trade-offs
Lock-free counters can still bottleneck because every increment hits the same cache line, causing false sharing and cache invalidation storms. Interviewers often expect mitigation ideas: per-thread or per-core counters combined at read time, exponential backoff loops when contention is detected, or combining counters with release/acquire barriers to reduce the need for seq_cst operations. Finally, highlight deployment considerations such as cross-process usage. `std::atomic<T>::is_lock_free()` should return true if the type can be safely placed in shared memory; otherwise, you may need platform-specific primitives or `std::atomic_ref` bound to aligned storage shared between processes.
